Release Overview
ESDc is a rules engine that enables us to enrich alerts after HITL alert generation (or draft) or modelset autoalert generation; these enrichments are then used to route the alerts to our customers more effectively.


ESDc = Enhanced Stream Definition capability.
Key Details
Business Value
* Who is the intended user? Content Engineers, working closely with Content Owners (Product Managers and DE Leads).
* What use cases are we solving for? ESDc enables us to enrich alerts based on certain characteristics. These enrichments enable us to route certain alerts to certain external levers (topics, keyword matching), ultimately reducing noise for our customers so they can focus on the alerts that matter.
* What ESDcs are currently live? We currently have ~100 ESDcs that are used for:
   * Pulse Topic Lists (~50% of all external topics in Pulse’s Topic List are populated exclusively via ESDc)
   * Cyber First Alert routing (First Alert is able to receive cyber content via querying for certain Alert Reference Terms in their Custom News Alerts watchlists)
   * Coming soon - Brand Risk List (100% of all upcoming Brand Risk Module topics will be populated by ESDc)
How to build ESDcs
* Where can I build streams? In Athena in the “ESDc” tab; “view” and “edit” access to this tab are gated by default and available on request. ESDc has borrowed the UI of AI Streams, so ESDcs can be complex, heavily nested booleans using operators like NOT, OR, AND just like AI Streams (ESDcs do not, however, inherit the filters of AI Streams).

* What constraints are there on inputs and outputs?
Area
	Constraints
	Matching
	1. Users are unable to write strings longer than trigrams.
2. Users are confined to the matchable fields / ESDc filters described above (however more can be added on request).
3. The character “$” is not accepted.
	Output labels
	1. Users are confined to the output labels described above (for example, today, users cannot output to the ‘subcaption’ field) (more output fields can be added on request).
	



* When do ESDcs run? ESDcs run after:
   * A human agent saves a draft of an alert in Apollo[ag]
   * A human agent endorses an alert in Apollo
   * An auto-alert is generated
Operational workflow for making an ESDc update (building new streams / updating existing ones)
Releases cannot be concurrent and thus must be queued; the ESDc Product Manager (Sophie Ishak) currently manages that queue. Here are the steps that we follow:


1. Content Engineer: [Prior] execute analysis for the change you’d like to make (presumably conducting research against alert data and patterns)
2. Content Engineer: Solicit approval if appropriate given the nature of the update (pre-approval at this point in the workflow is wise for the sake of efficiency). [Stakeholder Checkpoint A]


Update Type
	Requirements / stakeholders
	#1 Maintenance of existing content space (AKA editing an existing ESDc, breaking some existing ones up, where ultimately the outputs (internal topic counts and ART counts) are the same as prior to the release) 
	No approval needed - work directly with the ESDc PM


However notify team if there is a significant change in alert volume or thematic change in alert output (see #3 on whom to notify)
	#2 Creating new esdcs against existing topics that haven’t previously been labeled via ESDc
(e.g. Team assesses that existing topic “Drones” is stale, and although it hasn’t previously been labelled up via ESDc before, deserves additional routing through it (as a backstop/to capture fresh content)).
	No approval needed - work directly with the ESDc PM

	#3 Creation of net new content space - no new ARTs (AKA a significant update in existing ESDcs, or creation of net new ESDcs, with the intent of generating net new customer outputs. Those outputs are only internal topics (there are no new alert reference terms))

Further Constraints
Category
	Constraint
	UX
	1. Users cannot create or delete ESDcs from the ESDc tab.
2. Users cannot easily see tags or other metadata added to ESDcs from the grid view.
	Releases
	1. When we release ESDcs, we take a snapshot of the library and upload it to stage (and review results) and prod accordingly. We do not have separate stage and production environments today. Because of this, we must be very careful not to upload anything that contains output labels and is a draft accidentally to production. Thus, releases must be queued / non-concurrent. 
2. Releases are not instant. Given the manual process described above, ESDcs cannot (and perhaps should not) have immediate effect when updated.

Nuances of Internal Topic Labeling logic in ESDc (“Uncategorized”)
* There are ‘parent:child’ relationships described here between a small set of internal topics.
* These state that if a 'child' has not been tagged for a given 'parent', tag the 'Uncategorized' topic for that parent (in the sheet we call it "childIsDefaultOther?")
* So for example, if Aviation - Physical , a 'parent' topic is tagged, but none of its 3 'children' have been tagged, then + Aviation - Physical - Non-Matching should be added to the alert.
* We did this because we wanted to make sure that, as we split up these topics using ESDcs (as part of a topic update to Pulse), no alerting was lost. The 'non-matching' internal topics catch all of those alerts that aren't matched to an ESDc and route them to the corresponding Uncategorized... external topic accordingly.
